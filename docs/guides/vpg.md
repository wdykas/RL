# Version-Point Gradients for Async GRPO

Async GRPO trains on rollouts generated by an older policy. With a maximum trajectory age of `L`, a batch can come
from weights `θ_g` that are up to `L` optimizer steps older than the current weights `θ_t`. The default path
evaluates the GRPO loss at `θ_t` and corrects for the mismatch with token-level importance sampling (IS):
`w = π_θt / π_θg`. When the policy moves quickly, the IS weights become heavy-tailed. The gradient estimate then has a
very large variance, and training can collapse.

Version-point gradients (VPG) remove the importance weights instead of correcting them:

1. The trainer keeps a snapshot of the weights of every version a buffered batch can come from.
2. For each batch, it swaps the generating version `θ_g` into the model and runs the forward and backward pass
   there. The PPO ratio and the IS weight are 1 at that point.
3. It swaps the current weights back and applies the normal optimizer step to `θ_t` with that gradient.

The loss, the advantage estimator and the optimizer are unchanged. The lag becomes a plain gradient delay.

With bitwise trainer/generator parity (`policy.megatron_cfg.batch_invariant_mode`), the trainer's log-probs at `θ_g`
equal the generator's log-probs bit for bit, so every IS weight is exactly 1. Exact `w = 1` requires bitwise
trainer/generator parity; without it VPG still removes the lag component, and the residual weight is numerical
mismatch only (visible in `train/version_point_parity`).

## When to Use It

- Use it for async GRPO with `max_trajectory_age_steps >= 1` when the IS weights become heavy-tailed. Signs of this
  are a growing `train/gen_kl_error`, `train/probs_ratio_max` far above 1, or a reward collapse that the synchronous
  or lag-1 run does not show.
- It is cheaper per step than the IS path: the trainer skips the log-prob pass at the current weights.
- It does not fix instability that also appears without lag (for example, a learning rate that is too high for
  synchronous GRPO).

## Requirements

`grpo.async_grpo.version_point_gradient=true` is validated at startup. It requires:

- async GRPO with the in-process replay buffer (`data_plane.enabled=false`);
- the Megatron policy with the distributed optimizer, Megatron DDP (not Megatron-FSDP), pipeline parallel size 1, no
  optimizer CPU offload, no `overlap_param_gather_with_optimizer_step`, and BF16 parameters (no `fp8_param`);
- non-colocated generation with `in_flight_weight_updates=false`, so that each rollout comes from one weight version;
- one optimizer step per rollout batch (`policy.train_global_batch_size` = prompts per step × generations per prompt);
- `policy.router_replay` disabled and `loss_fn.force_on_policy_ratio=false`.

Bitwise parity (`policy.megatron_cfg.batch_invariant_mode=true`) is not required. Without it, startup logs a warning:
the gradient is still taken at the generation weights, but the PPO ratio there is 1 only up to the trainer/generator
numerical mismatch.

## Configuration

```yaml
grpo:
  async_grpo:
    enabled: true
    max_trajectory_age_steps: 8
    in_flight_weight_updates: false
    version_point_gradient: true   # default: false
    version_point_snapshot_mode: full   # "full" (default) or "sparse_diff"
    version_point_snapshot_check: false # debug: verify sparse_diff rebuilds against full copies
loss_fn:
  use_importance_sampling_correction: true   # used by steps that fall back to the IS path
```

A step falls back to the IS path at `θ_t` when its batch mixes generation versions or its version has no snapshot.
Neither happens with the fixed-lead replay buffer and `in_flight_weight_updates=false`. Fallbacks are logged.

`version_point_snapshot_mode` selects how the snapshots are stored:

- `full` keeps one host copy of the rank's parameter shard per version.
- `sparse_diff` keeps one host copy of the newest version (the current weights at training time) and, for each
  older version `k`, the reverse diff from version `k + 1`: the index and old value of every word that the optimizer
  step changed. To rebuild version `t − k`, the trainer applies the diffs of versions `t − 1` down to `t − k` (newest
  first, so the oldest value of a word wins) to the current shard on the GPU. The rebuild is bitwise exact.
  `version_point_snapshot_check: true` also keeps full copies and verifies every rebuild against them (debug only;
  it costs the full-mode memory and a device-to-host comparison per step).

Snapshots are saved with every checkpoint under `<checkpoint>/policy/version_snapshots/` and restored on resume, so a
resumed run keeps computing every buffered batch's gradient at its generation weights. A `sparse_diff` run can resume
from a checkpoint written in `full` mode (the snapshots are converted on load).

## Metrics

| Metric | Meaning |
|---|---|
| `train/version_point_applied` | 1 if the step's gradient was taken at the generation weights, 0 on the IS path |
| `train/version_point_age` | current version minus the batch's generation version |
| `train/version_point_mixed_batch` | 1 if the batch mixed generation versions (IS path) |
| `train/version_point_no_snapshot` | 1 if the batch's version had no snapshot (IS path) |
| `train/version_point_parity` | max \|PPO ratio − 1\| over loss tokens on version-point steps; 0 under bitwise parity |
| `train/version_point_snapshot_gb` | host memory held by the snapshots per trainer rank (GB) |
| `train/version_point_swap_in_s` | time to rebuild and swap in the version point on this step (s) |
| `train/version_point_diff_frac` | fraction of the shard's words the newest optimizer step changed (`sparse_diff`) |
| `train/version_point_checks_passed` | rebuilds verified bitwise against full copies (`sparse_diff` with the check) |
| `timing/train/version_point_snapshot` | time to take the per-step snapshot |

`train/version_point_parity` is derived from `probs_ratio_min` / `probs_ratio_max` and needs the full loss metrics
(not `metrics_level: minimal`).

## Memory and Checkpoint Cost

Let `shard = 2 bytes × P_rank / DP` be one BF16 copy of a rank's distributed-optimizer shard, where `P_rank` is the
number of parameters on the rank after tensor/expert parallelism and `DP` is the data-parallel size. For Qwen3-8B with
2 trainer ranks (DP 2), `shard` is 8.2 GB.

- **Host (pinned) memory per rank:**
  - `full`: `(L + 1) × shard`. At `L = 8` that is 74 GB per rank (148 GB per node) for the 8B example; at `L = 32`,
    270 GB per rank.
  - `sparse_diff`: `shard + Σ_k 3 × frac_k × shard`, summed over the `L` kept diffs, where `frac_k` is the fraction of
    words step `k` changed (`train/version_point_diff_frac`); each changed word costs a 4-byte index and a 2-byte value,
    i.e. 3× its own size. For the 8B example at learning rate 3e-6 (1-2% of the words change per step), this measured
    11 GB per rank at `L = 8` and 23 GB per rank at `L = 32`.
- **GPU memory:** one extra copy of the rank's shard (8.2 GB for the 8B example) during the forward/backward pass, in
  both modes.
- **Checkpoint size:** the same host data per rank is written to every checkpoint (148 GB for the 8B example at
  `L = 8` in `full` mode).
- **Time:** one snapshot (device-to-host copy of the shard) per step and two all-gathers of the parameters per
  training step. The trainer skips its log-prob pass at the current weights.

## Reproduce a Result

The recipe `examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg.yaml` trains Qwen3-8B-Base on
MATH levels 3-5 (plain `User:/Assistant:` prompt, 16 prompts × 16 samples, validation on AIME 2024, AIME 2025 and
MATH-500) with async GRPO at `max_trajectory_age_steps=8`, learning rate 1e-5, batch-invariant kernels and VPG on.
It needs one node with 4 GPUs (2 trainer + 2 generation). On GB200 a step takes about 1 minute early in training
and grows with the response length.

```sh
# VPG
HF_HUB_OFFLINE=0 uv run examples/run_grpo.py \
  --config examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg.yaml \
  grpo.seed=1 grpo.max_num_steps=80 \
  logger.log_dir=results/vpg_l8/logs checkpointing.checkpoint_dir=results/vpg_l8/ckpt

# IS baseline at the same lag
HF_HUB_OFFLINE=0 uv run examples/run_grpo.py \
  --config examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg.yaml \
  grpo.async_grpo.version_point_gradient=false \
  grpo.seed=1 grpo.max_num_steps=80 \
  logger.log_dir=results/is_l8/logs checkpointing.checkpoint_dir=results/is_l8/ckpt
```

In a 40-step run of each command (seed 1), validation accuracy (AIME 2024 + AIME 2025 + MATH-500) was:

| step | 0 | 10 | 20 | 30 | 40 |
|---|---|---|---|---|---|
| VPG | .646 | .755 | .784 | .790 | .742 |
| IS | .645 | .771 | .775 | .759 | .433 |

The VPG run took the version point on every step (`train/version_point_applied` = 1) with
`train/version_point_parity` = 0. In the IS run, `train/gen_kl_error`, the generator/trainer mismatch that the IS
weights correct, grew from 4e-4 at step 2 to 0.11 at step 39, and the mean validation response length grew to 5,756
tokens (VPG: 3,517). The VPG run's step was also 10% shorter (64 s vs 71 s median), because it skips the log-prob
pass at the current weights.
